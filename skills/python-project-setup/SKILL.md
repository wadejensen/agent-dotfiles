# python-project-setup

Scaffold a minimal, boring Python project. `uv` manages the venv, the
lockfile, and the Python version. Everything runs through `setup.sh`,
`run.sh`, `test.sh` — nobody has to remember a `uv run` incantation.

Don't add anything beyond what's templated here (extra config files, CI,
pre-commit, docker) unless asked. Small project, small footprint.

## Steps

1. Ask (or infer from context) two names:
   - `PROJECT_NAME` — directory / repo name, kebab-case (e.g. `log-tailer`)
   - `PACKAGE_NAME` — importable package name, snake_case (e.g. `log_tailer`)
2. Copy every file under `templates/` into the target project root, preserving
   the directory structure, and rename the `PACKAGE_NAME` directory
   (`templates/src/PACKAGE_NAME`) to the real package name.
3. Replace the literal placeholders `PACKAGE_NAME` and `PROJECT_NAME` in every
   copied file (including inside file contents) with the real values, e.g.:
   ```
   grep -rl 'PACKAGE_NAME\|PROJECT_NAME' . | xargs sed -i '' \
     -e "s/PACKAGE_NAME/actual_package_name/g" \
     -e "s/PROJECT_NAME/actual-project-name/g"
   ```
   (drop the `''` after `-i` on Linux)
4. `chmod +x setup.sh run.sh test.sh`
5. Run `./setup.sh` — it must succeed from a bare clone with nothing but
   `bash`, `curl`, and `git` present (see setup.sh below for what it
   bootstraps).
6. Run `./test.sh` to confirm type checks and tests pass on the scaffolded
   template (they should — `test_cli.py` just exercises the example command).
7. If this is a fresh repo, `git init` and let the user review before any
   commit — don't commit on their behalf.

## What's templated

- `setup.sh` — installs `uv` if missing, pins the Python version, runs
  `uv sync` to create `.venv` and the `uv.lock` lockfile. Idempotent: safe to
  re-run any time, e.g. after pulling new dependencies.
- `run.sh` — runs the app via its click entrypoint with sane default flags,
  forwarding any extra args.
- `test.sh` — runs `mypy` then `pytest`. Type errors fail the script before
  tests even start, so a broken type doesn't hide behind a green test suite.
- `pyproject.toml` — project metadata, `click` runtime dependency, `pytest`
  + `mypy` as a `dev` dependency group, `project.scripts` entrypoint.
- `src/PACKAGE_NAME/cli.py` — one click command (`--verbose` flag, logging
  set up in main). Add more commands/subcommands only when the project
  actually needs more than one — a single command is not a reason to switch
  to `click.group()`.
- `tests/test_cli.py` — one integration-style test using
  `click.testing.CliRunner` against the real command, not a mocked one.
- `.gitignore` — `.venv`, `__pycache__`, etc. `uv.lock` is NOT ignored — it's
  committed, same as any other lockfile.
- `README.md` — minimal setup/run/test pointer. `pyproject.toml` sets
  `readme = "README.md"`, and the build backend fails without a file at that
  path, so this one isn't optional.
- `.vscode/settings.json` — points the editor at `.venv` and turns on
  `python.analysis.useLibraryCodeForTypes` so go-to-definition/implementation
  works into third-party library code, not just project code.
- `.vscode/extensions.json` — recommends `ms-python.python` +
  `ms-pyright.pyright`. Pyright, not Pylance: Pylance's license blocks it in
  non-Microsoft builds (Cursor, VSCodium, etc.), so Pyright is the one choice
  that works for every contributor regardless of editor.

## Notes

- `uv.lock` is generated by `uv sync`/`uv lock`, never hand-written. If asked
  to "add a dependency", run `uv add <package>` (or `uv add --dev <package>`
  for dev-only tools) and let it update `pyproject.toml` + `uv.lock` — don't
  hand-edit either file.
- Don't add type-check suppressions or `# type: ignore` to make `test.sh`
  pass — fix the type, or ask if it's genuinely a false positive.
- Keep `run.sh`'s defaults to things a human would otherwise type every time
  (e.g. `--verbose` while iterating). Don't bake in flags that hide real
  configuration a user is likely to want to change.
